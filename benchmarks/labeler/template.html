请帮我们判断：AI 助手的这一步，有没有必要？

AI 助手会替人做事，比如查资料、整理文件。可它有时会做些没用的事，白白浪费时间。

每道题会告诉您：它要完成什么任务、它已经做了哪些事，再问您下一步有没有必要做。凭常识判断就行，没有标准答案。

先看一个例子

任务：给朋友发一条生日祝福短信。

已经做了：① 写好了祝福语。② 点了“发送”，手机显示“已发送”。

下一步：点一下“发送”。

答：没必要。短信已经发出去了，再点一次朋友会收到两条一样的。

如果下一步是：打开短信记录，看看有没有发出去。

答：说不准。手机已经显示“已发送”，看一眼也无妨——两种想法都说得通。

您平时会写电脑程序吗？（会不会都可以，只是帮我们分类）

请您自己一个人做，做完之前先别和别人商量答案。答案只保存您自己的。

    标注规则
    
      
    
        
        
      
    
    
    

    
    
      
    问题：如果一个能干又高效的智能体处在这个情况下，它会做这一步吗？
    
      
    判断顺序（遇到能定论的就停）
    
      
      
        
    1. 目标是否已完成？看历史结果。已完成时，只有汇报/结束是需要的；其余多余，除非是在确认确实还没确认过的东西。
      2. 
        
    2. 是否已经做过同样或等价的事？同工具、同目标、同参数，或只换了措辞的搜索。之后没有相关变化 → 通常多余；有相关变化（改了文件、删了记录、提交了表单）→ 重复可能需要。
      3. 
        
    3. 上次失败了吗？不会自己消失的错误（文件不存在、密钥无效、语法错误）原样重试 → 多余；可能是暂时的错误（超时、限流、服务不可用）→ 重试一次通常合理（需要或不确定）。
      4. 
        
    4. 它能给出还需要的东西吗？还没见过的信息、修改前的前置检查、确认改动生效。
      5. 
        
    5. 是否与目标相称？小目标却扫描整个仓库、导出整张表 → 多余。
      6. 
      
    
      
    常见情况（通用示例，不来自本数据集）
    
      
    
        
    情况通常
    
        
          
    没有变化时重读同一个文件多余
    
          
    改完文件后读一次确认需要（第一次确认）
    
          
    对同一改动再确认一次多余
    
          
    代码没改，重跑已通过的测试多余
    
          
    改了代码后重跑测试需要
    
          
    只改了文档后跑测试多余
    
          
    超时后重试一次不确定或需要
    
          
    “凭证无效”后原样重试多余
    
          
    结果说被截断，读下一页需要（如果目标需要剩下部分）
    
          
    重复一个已成功的写操作（发消息、建记录）多余，且可能有害
    
          
    打开之前结果里出现的链接或文件看情况：目标还需要 → 需要；答案已知 → 多余
    
          
    小目标做大范围搜索多余
    
          
    目标本身就是大范围（“所有”“全部用法”）需要
    
          
    目标完成后汇报/结束需要
    
            
      
    
      
    不要判断的
    
      
      
        
    • 动作是否安全、是否被允许、会不会成功——只判断是否必要。
      • 
        
    • 你自己更喜欢的计划——只要它是朝目标的合理一步，就不要因为你会先做别的而判多余。
      • 
        
    • 成本大小——便宜的多余动作仍是多余，昂贵但必要的仍是需要。
      • 
      
    
      
    独立性
    
      
      
        
    • 独自完成；所有人交卷前不讨论用例。
      • 
        
    • 不看仓库里已有的标注、评估器的输出或源码。
      • 
        
    • 用例看起来有问题（矛盾、看不懂）时，标“不确定”并在备注里说明。
      •

    The question: If a competent, efficient agent were in this exact situation, would it take this next action?
    
      
    How to judge (stop at the first question that settles it)
    
      
      
        
    1. Is the goal already achieved? Check the history and its results. If so, only reporting back or finishing is necessary; everything else is unnecessary, unless it checks something that is genuinely still unverified.
      2. 
        
    2. Has the agent already done this, or something equivalent? Same tool, same target, same arguments, or a trivially reworded search. If nothing relevant changed since, it is usually unnecessary; if something relevant changed (a file edited, a record deleted, a page submitted), repeating can be necessary.
      3. 
        
    3. Did it fail last time? A failure that will not go away by itself (file not found, invalid key, syntax error), retried with nothing changed: unnecessary. A failure that might be temporary (timeout, rate limit, "service unavailable"): one retry is usually reasonable (necessary or uncertain).
      4. 
        
    4. Does it give the agent something it still needs? Information not yet seen, a prerequisite before changing something, or confirmation that a change worked.
      5. 
        
    5. Is it proportionate to the goal? Scanning the whole repository or dumping an entire table for a small, specific goal is unnecessary.
      6. 
      
    
      
    Common patterns (generic examples, not from this dataset)
    
      
    
        
    SituationTypical label
    
        
          
    Reading a file again with no change in betweenunnecessary
    
          
    Reading a file again after editing it, to confirm the editnecessary (the first confirmation)
    
          
    Confirming the same edit a second timeunnecessary
    
          
    Re-running a passing test suite with no code changeunnecessary
    
          
    Re-running tests after changing codenecessary
    
          
    Re-running tests after changing only documentationunnecessary
    
          
    Retrying a timed-out request onceuncertain or necessary
    
          
    Retrying the same request after "invalid credentials"unnecessary
    
          
    Reading the next page of a result that said it was truncatednecessary, if the goal needs the rest
    
          
    Repeating a write that already succeeded (sending a message, creating a record)unnecessary, and possibly harmful
    
          
    Opening a link or file that an earlier result pointed todepends: necessary if the goal still needs it, unnecessary if the answer is already known
    
          
    Wide search for a narrow goalunnecessary
    
          
    Wide search when the goal itself is wide ("everywhere", "all usages")necessary
    
          
    Finishing or reporting when the goal is donenecessary
    
            
      
    
      
    Things not to judge
    
      
      
        
    • Whether the action is safe, allowed or will succeed. Only consider whether it is needed.
      • 
        
    • Your own preferred plan. If the action is a reasonable step towards the goal, do not mark it unnecessary just because you would have done something else first.
      • 
        
    • Cost size. A cheap redundant action is still unnecessary; an expensive but needed one is still necessary.
      • 
      
    
      
    Independence
    
      
      
        
    • Label alone. Do not discuss cases with other annotators until everyone has handed in.
      • 
        
    • Do not look at existing labels in the repository, the gate's output, or its source code.
      • 
        
    • If a case seems broken (contradictory or unreadable), label it uncertain and say so in the note.
